# October 2026 dependency remediation

## Scope and verification boundary

Seven public service dependency graphs and their container build tools. Python 3.11.17 and certifi 2026.10.19 were already pinned. These source changes do not prove that a deployed service has restarted. Deployment owners must record installed graphs, process interpreter paths, restarts and live checks separately.

## Confirmed affected pins

Targets below cover all nonwithdrawn advisories returned for the baseline pins, plus advisories introduced along the upgrade path. Supporting metadata was obtained from GitHub Global Security Advisories and OSV on 2026-10-23. Unused Flask-OAuthlib, requests-oauthlib and oauthlib were removed; application OAuth uses Authlib. AWS SDK companion, Flask integration and HTTP parser pins move together to keep dependency constraints valid.

## Attack surface

HTTP parsing, templates, uploaded/form data, OAuth responses, outbound HTTP redirects/proxies, ASN.1/cryptographic parsing and CLI credential files are the applicable library surfaces. Some advisory paths are not invoked by these apps (for example Jinja sandbox execution and PKCS#7 decryption); patched versions avoid carrying those vulnerable implementations. Together SDK 0.2.8 remains because it has no reported applicable advisory and its legacy API is exercised by tests. Pillow, wheel extraction commands, PHP, Electron and ML checkpoint loading are absent from application source/dependency graphs. Wheel and setuptools are still patched explicitly in every image because build tools are installed files, even when extraction is not an application route.

## Tests and rollback

Python 3.11.17 isolated environments resolved the complete service graphs; `pip check` passed. OSV batch audits of both complete installed graphs, including transitive and build/test packages, returned no advisories. Seven offline service probes exercise actual Flask/Quart routes; the portal probe also runs all four existing OpenAPI fixtures. DB, provider API, S3 and model catalog boundaries are mocked, and unmocked socket connections fail. Tests caught a missing `os` import in Together completion, fixed in this change. CI independently installs and checks each service, then also jointly resolves all six shared-environment requirement files and runs each app in that same installed environment. Together is separately resolved and tested, matching its separate deployment venv.

Rollback: revert this commit and redeploy the previous tested image/venv snapshot if compatibility fails. That restores known vulnerable pins; do not treat rollback as a security fix. Source merge, image build, installed venvs and running workers must be verified separately.

cryptography 50.0.2 also preserves the deployed security floor and uses OpenSSL 4.0.3 in published wheels; see the [official release notes](https://cryptography.io/en/latest/changelog/#v50-0-2).

## Separate source authentication fixes

The proxy previously accepted any Basic token whenever an action had an auth record: `validate_auth` unconditionally returned true. It now strictly decodes Basic credentials, compares the case-sensitive username, checks the stored bcrypt password hash, and rejects malformed/oversized credentials, missing hashes and unknown auth schemes before creating an upstream request. Invalid authentication returns HTTP 401. Proxy authentication credentials are removed before forwarding; only separately configured upstream credentials are injected. bcrypt 4.0.1 is explicitly installed in portal/proxy because it is compatible with the existing passlib 1.7.4 password hashes; the installed package has no advisory in the audit database at verification time. Existing hashes and generated API keys remain valid.

The proxy no longer writes raw request headers/body or action/API configurations to process logs. Authorization, Cookie, Proxy-Authorization and configured credential header names are redacted before request logs are stored in CouchDB. Known proxy/API credentials are also removed from logged request bodies, query parameters and upstream response fields, including JSON/URL-encoded representations; client-visible forwarding and responses are preserved. Application request/response logging remains functional; payloads can still contain user data by design, so access to the log database must remain restricted.

The portal refuses to start without a nonempty private FLASK_SECRET or when it is the known `development` default. Deployment owners must verify a persistent secret is already configured before activation. Generating/changing it signs out existing sessions. Offline tests cover correct/wrong passwords, mixed-case Basic scheme with case-sensitive token, missing/malformed credentials, unknown auth records, zero upstream calls on failures, credential redaction and portal secret enforcement.

These are source defects found directly in the application, with no assigned upstream advisory ID. Rollback is a commit revert plus previous artifact restore; that reintroduces the authentication bypass. Independently restrict direct access to backend services so client requests pass through the proxy authentication boundary.
